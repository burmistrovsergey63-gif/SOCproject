# Технический отчёт: интеграция Comdi → Eventicious

**Дата:** 09.10.2026
**Статус:** работает в бою, 82/82 эпизода синхронизированы
**Назначение:** передать разработке для анализа и дальнейшей поддержки

---

## 1. Постановка задачи

Клиент передал ссылку на свой API расписания и попросил забирать данные оттуда
и загружать в нашу систему.

| | Источник | Приёмник |
|---|---|---|
| Система | Comdi (broadcast) | Eventicious External API v2 |
| URL | `https://broadcast.comdi.com/api/player/event/erzo3310` | `https://api-integration.eventicious.ru` |
| Метод | `GET`, без авторизации | `POST/PUT/DELETE`, `Bearer`-токен |
| Объём | ~1 МБ JSON | — |
| Чтение | — | **GET отсутствует** для расписания/залов/тем |

Схема, которую прислал клиент, оказалась подмножеством реальной: в ней
не было `timeStart`/`timeStop`, без которых расписание бессмысленно.

---

## 2. Что реально отдаёт источник

Проверено на живом запросе. Payload — всё целиком (стримы, викторины, чаты,
магазин, участники), расписание — малая часть.

```
5 залов (stream) → 82 эпизода (episode) → 7 тем (tags)
```

Ключевые особенности данных:

- `timezone: null` — время приходит unix-seconds UTC, пояс задаём сами.
- У 2 залов (`Молекула`, `Атом`) `episode` — **пустой массив**, не `null`.
- `info_ru` пуст у **всех** 82 эпизодов.
- `color` у залов — `90baff` **без `#`**, API ждёт `#90baff`.
- `hidden: false` у всех; `speakers: []` у всех.
- Теги: `{id, titleRu, titleEn, color}`.

---

## 3. Что принимает приёмник

Аутентификация: `client_credentials` → `POST /connect/token` → `Bearer`.

| Объект | Create | Update | Delete |
|---|---|---|---|
| Зал | `POST /locations/create` | `PUT /locations/update/{id}` | `DELETE /locations/delete/{id}` |
| Тема | `POST /tags/create` | `PUT /tags/update/{id}` | `DELETE /tags/delete/{id}` |
| Эпизод | `POST /sessions/create` | `PUT /sessions/update/{id}` | `DELETE /sessions/delete/{id}` |

Важные свойства API, выясненные опытным путём:

1. **Нет GET** для этих сущностей — прочитать текущее состояние невозможно,
   приёмник принимает только write. Это главное ограничение архитектуры.
2. **ID задаёт наша система** (`id` в теле create). Связи объектов — тоже
   через наши id (`tagIds`, `locationsIds`, `speakersIds`).
3. `create` на занятый id → `400`/`409` с телом
   `"Session with this id already exists in the database"`.
4. **Нельзя два события в одном зале в одно время** → `409 Conflict`.
5. `404` может прийти сразу после успешного `create` — задержка консистентности.
6. Переводы: `PUT` с полем `language` (`ru-RU` / `en-US`). Без поля — основной язык.
7. Успешный ответ — всегда `200`.

## 4. Архитектура решения

```
comdi_sync/
  config.py        114 строк   настройки из окружения (.env)
  comdi.py         186 строк   GET источника + нормализация payload
  eventicious.py   210 строк   токен, ретраи, CRUD-обёртки
  state.py         148 строк   SQLite: маппинг id + хэши + журнал
  sync.py          420 строк   логика синхронизации
  __main__.py      130 строк   CLI: once | loop | dry
```

Поток данных:

```
Comdi GET → normalize() → Schedule{halls, tags, episodes}
                ↓
        sync_halls()   → locations     (первыми: на них ссылаются эпизоды)
        sync_tags()    → tags
        sync_sessions() → sessions
                ↓
   diff по sha256 → create | update | delete | "не шлём вообще"
                ↓
        sync_state.sqlite3
```

### Решение главного ограничения

Поскольку GET нет, вся правда о том, что уже отправлено, живёт локально:

```sql
CREATE TABLE objects (
    entity       TEXT,    -- location | tag | session | location_dup | session_hall
    source_id    INTEGER, -- id в Comdi
    target_id    INTEGER, -- id, который мы передали в Eventicious
    content_hash TEXT,    -- sha256 последнего отправленного payload
    en_hash      TEXT,    -- sha256 отправленной EN-версии (своя, для ретраев)
    updated_at   TEXT,
    PRIMARY KEY (entity, source_id)
);
```

Алгоритм на каждый прогон: `sha256(payload)` → сравнить с `content_hash` →
совпало, значит ничего не менять. На практике это даёт **0 HTTP-запросов**,
когда данные не изменились.

Детерминированные ID (`source_id + offset`) позволяют восстановить работу
при потере локальной БД: объекты переиспользуются, а не дублируются.

## 5. Обнаруженные инциденты и как закрыты

### 5.1. Пересечение времени в зале (единственный `409`)

В данных SOC Forum 2026 зал «Кинетика» содержит два доклада одновременно:

| Comdi id | Название | Время |
|---|---|---|
| 75111 | Поиск малозаметной C2-активности в сетевом трафике | 13:15–13:45 |
| 75117 | AI в контуре SOC: от анализа аномалий… | 13:15–13:45 |

Eventicious это отвергает. Проверено: из 82 эпизодов конфликт ровно один.

**Решение (согласовано):** при `409` создаётся дубль зала
«Зал Кинетика (2)» (`id = source + offset_location + 1_000_000`), конфликтный
эпизод переводится туда, перенос фиксируется в `session_hall`.

**Побочный эффект, который был и устранён:** перенос изначально запоминался
только при отправке, но в состояние сохранялась исходная привязка → хэш
расходился каждый прогон → `75117` обновлялась бесконечно. После выноса
override в отдельную таблицу стала стабильность 0/0/0.

### 5.2. Зомби-запись: `create` → 409, `PUT` → 404, `DELETE` → 404

Объект «занят» в индексе уникальности, но недоступен на чтение/правку.

**Решение:** `create` при конфликте автоматически переключается на `update`
тем же payload'ом — так объекты, созданные раньше, приводятся к актуальному
состоянию, а не остаются устаревшими.

### 5.3. `404` сразу после `create`

Задержка консистентности: `create` уже ответил `200`, а `update` сразу за ним
— ещё `404`.

**Решение:** `update` повторяет `404` до 3 раз с паузой 2 с.

### 5.4. Один сбой ронял весь прогон

Изначально исключение на первом же проблемном эпизоде обрывало прогон —
остальные 81 не загружались.

**Решение:** ошибки собираются в список, прогон идёт до конца, в конце —
итог со счётчиком `failed`, код возврата `1` при частичном результате
(нужен cron/мониторингу).

### 5.5. EN-версия терялась молча

Английский `PUT` шёл сразу после `create` и при `404` просто логировался —
повтора не было, перевод не применялся до следующего изменения payload.

**Решение:** у EN-версии собственный `en_hash`, не зависящий от основного
payload. Не ушла → не записана → повторится на ближайшем прогоне.

## 7. Как управлять

```bash
python -m comdi_sync dry    # показать payload, ничего не записывая
python -m comdi_sync once   # один прогон (cron)
python -m comdi_sync loop   # фоновый опрос каждые SYNC_INTERVAL_SECONDS
```

Cron: `*/5 * * * * cd /path && .venv/bin/python -m comdi_sync once >> sync.log 2>&1`

**Источник истины — Comdi.** Изменения в расписании вносить там; правки,
сделанные напрямую в админке Eventicious, будут перезаписаны при следующем
изменении данных в Comdi.

## 8. Открытые вопросы

1. **Часовой пояс** — в Comdi `timezone: null`, стоит `Europe/Moscow`. Подтвердить.
2. **Пересечение `75111`/`75117`** — дубль зала решает технически, но правильнее
   поправить время в Comdi; тогда дубль и override снимутся автоматически.
3. **`hidden`-эпизоды** — сейчас не фильтруются, уедут как обычные.
4. **Докладчики** — `speakers: []` у всех; `speakersIds` собираются
   (`id + ID_OFFSET_USER`), но `sync_speakers` не реализован, данных нет.
5. **`info_ru` пуст у всех 82** — ожидает ли клиент описания?
6. **`DELETE_REMOVED=true`** — при удалении эпизода в Comdi он удалится и у нас.
   Возможна альтернатива: `false` + отдельная команда `prune` для явного удаления.
