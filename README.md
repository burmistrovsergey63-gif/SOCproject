# Comdi → Eventicious: синхронизация расписания

Забираем боевую программу по API Comdi и загружаем её в нашу систему
(Eventicious External API v2).

```
GET  https://broadcast.comdi.com/api/player/event/erzo3310   (Comdi, источник)
  ↓
нормализация: stream[] → залы, episode[] → эпизоды, tags[] → темы
  ↓
POST/PUT/DELETE https://api-integration.eventicious.ru/api/external/v2/...  (приёмник)
```

## Установка

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env       # и вписать боевые client_id / client_secret
```

## Запуск

```bash
.venv/bin/python -m comdi_sync dry    # посмотреть, что уйдёт в API (ничего не пишет)
.venv/bin/python -m comdi_sync once   # один прогон — для cron
.venv/bin/python -m comdi_sync loop   # постоянный опрос каждые SYNC_INTERVAL_SECONDS
```

Cron (раз в 5 минут):

```cron
*/5 * * * * cd /path/to/project && .venv/bin/python -m comdi_sync once >> sync.log 2>&1
```

## Как это работает

1. **Забираем** у Comdi весь payload (~1 МБ) и вырезаем только расписание.
2. **Залы → locations**, **темы → tags**, **эпизоды → sessions**.
   Порядок важен: залы и темы синхронизируются первыми, на них ссылаются эпизоды.
3. **Идемпотентность через локальную SQLite** (`sync_state.sqlite3`):
   - храним `source_id (Comdi) → target_id (Eventicious)` и хэш отправленного payload;
   - если хэш не изменился — запрос не шлём вообще;
   - изменилось — `PUT update/{id}`;
   - объекта раньше не было — `POST create`;
   - пропал из Comdi — `DELETE` (отключается `DELETE_REMOVED=false`).
   Это обязательно, потому что **в API приёмника нет GET** для расписания —
   читать текущее состояние обратно нельзя.
4. **ID** детерминированы: `id_в_нашей_системе = id_в_Comdi + смещение`
   (`ID_OFFSET_*` в `.env`). Смещение нужно, чтобы не пересечься с объектами,
   которые уже заведены вручную.
5. **Время**: Comdi отдаёт unix-UTC, Eventicious ждёт локальное `YYYY-MM-DDTHH:MM`.
   Часовой пояс берётся из `EVENT_TIMEZONE` (в ответе Comdi поле `timezone` = null,
   поэтому задаём сами — сейчас `Europe/Moscow`).
6. **Языки**: создание идёт на основном языке, английская версия
   отправляется вторым `PUT` c `language: en-US` (отключается `SYNC_EN=false`).
   У EN-версии свой хэш — при сбое она повторяется на следующем прогоне,
   не дожидаясь изменений основного payload.

## Устойчивость

- Ошибка на одном эпизоде **не роняет прогон**: остальные грузятся, в конце —
  список неудачных, код возврата `1` (для cron/мониторинга).
- `create` при занятом id (409 / «already exists») автоматически переключается
  на `update` — так приводим к актуальному состоянию объекты, созданные раньше.
- `update` повторяет `404` (задержка консистентности API: create уже ответил 200,
  а update сразу после — ещё 404).
- Токен обновляется автоматически при `401`; сетевые ошибки и `5xx` ретраятся
  с экспоненциальной задержкой.

## Пересечение времени в зале

Eventicious запрещает два события в одном зале в одно время (`409 Conflict`).
В данных SOC Forum 2026 такое есть ровно один раз: в зале «Кинетика» идут
параллельно `75111` («Поиск малозаметной C2-активности…») и `75117`
(«AI в контуре SOC…»), оба 13:15–13:45.

**Конфликты считаются по данным Comdi (`_plan_halls`), а не по `409` от API.**
Это принципиально: если полагаться на ответ API, то обычный обмен двумя
докладами местами даёт ложный конфликт — оба слота ещё заняты, пока мы не
успели кого-то сдвинуть — и в системе без нужды появляется дубль зала.

Алгоритм: эпизоды зала сортируются по началу, дальше жадно раскладываются
по «дорожкам». Дорожка `0` — основный зал, `1`, `2`… — его дубли
(«Зал Кинетика (2)», «(3)»…). id дубля детерминирован:
`hall_id + ID_OFFSET_LOCATION + lane * 1_000_000`.

Следствия:

- обмен докладов местами **не создаёт** дублей — оба уходят на дорожку `0`;
- когда клиент уберёт пересечение в Comdi, эпизод **сам вернётся** в основной
  зал: дорожка снова станет `0`. Отдельного override-состояния нет — план
  пересчитывается на каждом прогоне, поэтому «залипнуть» в дубле нельзя;
- если `409` всё же прилетело (планировщик что-то не учёл), эпизод грузится
  **без зала** и пишется громкая `ERROR` — данные не теряются, проблема видна.

## Ограничения API приёмника

Зафиксировано опытным путём — это свойства Eventicious, а не баги синка:

- **Нет транзакций.** Обмен двумя докладами местами в одном зале нельзя
  выполнить атомарно. Вручную это делается в три шага: время у первого →
  у второго → снова у первого. Наш код такого не делает: он не двигает
  время, а распределяет по дорожкам, поэтому ритуал не нужен.
- **`locationsIds: []` не очищает привязку к залу** — API игнорирует пустой
  массив. Освободить слот явным образом нельзя.
- **Нет GET** для расписания/залов/тем — читать текущее состояние обратно
  нельзя, всё хранится локально.

## Тонкости данных Comdi

- У части залов (`Зал Молекула`, `Зал Атом`) `episode` — **пустой массив**, не `null`.
  Зал всё равно должен попасть в систему.
- `info_ru` у всех 82 эпизодов сейчас пустой — description будет пустым, это норма.
- `color` у залов — `90baff` без `#`; API ждёт `#90baff`. Конвертируется автоматически.
- `hidden` у эпизодов сейчас всегда `false`; если начнут скрывать — поле пока
  не транслируется, при необходимости добавим.
- Схема из письма клиента — подмножество реальной: в эпизодах есть ещё
  `timeStart/timeStop`, `status`, `speakers`, `section_ru` и т.д.

## Структура

```
comdi_sync/
  config.py       # настройки из окружения
  comdi.py        # источник: запрос + нормализация payload
  eventicious.py  # приёмник: токен, retry, CRUD-обёртки
  state.py        # SQLite: маппинг ID + хэши + журнал прогонов
  sync.py         # логика синхронизации
  __main__.py     # CLI: once | loop | dry
```
